# Policy: Integration Security

Apply these constraints when generating any integration spec. Flag any violation or gap as an Area of Concern with the owner named below.

---

## Authentication

- **Preferred:** OAuth 2.0 (client credentials flow) for API-to-API communication.
- **Acceptable:** API key for read-only flows or when the target system vendor mandates it.
- **Required only when vendor mandates:** Mutual TLS.
- The authentication method used for every system integration point must be documented in the **Source System Integration Points** section of the spec.
- If the intent does not specify an authentication method, carry this forward as an open item and note it as a concern.

## Secrets Management

- API keys, tokens, OAuth client secrets, and credentials must **never** be hardcoded in integration code or configuration files.
- Reference secrets by name only in the spec, e.g.: "stored in AWS Secrets Manager as `crm-api-key`".
- Secrets provisioning is the client's responsibility. The spec must note this in the Responsibilities section.

## PII Handling

The following field types are classified as PII and require special handling:
- Full name, first name, last name
- Email address
- Phone number
- Physical address
- Social Security Number / Tax ID / National ID
- Date of birth
- Financial account numbers, card numbers
- Any field labeled "sensitive" or "confidential" in the source system schema

**Rules for PII fields:**
- PII must not be logged in plaintext in any operational log (CloudWatch, Splunk, etc.). Mask or exclude PII fields from log output.
- PII must not be stored outside the client's approved cloud region.
- PII fields in the field mapping table must include "PII — do not log" in the Notes column.

**Concern trigger:** If a PII field is included in the payload and the destination system or logging destination is outside the client's approved cloud region, flag as a concern with owner: Legal / Compliance.

## Encryption

- All data in transit must use TLS 1.2 or higher.
- Data at rest in queues (SQS, Service Bus), storage (S3, Blob), and database (RDS, CosmosDB) must use the cloud provider's managed encryption (AES-256 or equivalent). The spec does not need to configure this explicitly — it should note "standard cloud provider encryption at rest applies."

## Access Scope

- Integration runtime credentials must be scoped to the minimum permissions required for the integration to function.
- No wildcard permissions (e.g., `s3:*`, `iam:*`).
- The spec should describe the permission scope required, not the IAM policy syntax.
