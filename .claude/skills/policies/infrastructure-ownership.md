# Policy: Infrastructure Ownership

Apply these constraints when generating any integration spec. These rules define the boundary between what the implementation vendor builds and what the client owns.

---

## Core Ownership Model

| Item | Owner |
|------|-------|
| Integration runtime code | Implementation vendor |
| Cloud infrastructure (compute, queues, storage, secrets) | Client — provisions, owns, and pays |
| Client data | Client — the implementation vendor does not host client data in its own cloud accounts |
| Production access | Client — vendor has time-limited, logged access during development only |
| Sandbox / test environment | Client — provisions; vendor uses during development |
| Test data in sandbox | Client — responsible for accuracy and representativeness |
| Composite key / translation table content | Client (operations team) |
| Third-party API credentials | Client — requests from vendor; provisions to secrets manager |
| Production monitoring and alerting | Client — unless a managed services agreement is in place |

**Rule:** The Responsibilities table in the spec must clearly assign every task to either the implementation vendor or the client. No task may be left unassigned.

## Cloud Infrastructure

- The client provisions, owns, and pays for all cloud infrastructure used by the integration.
- The implementation vendor does not host client data in its own AWS or Azure accounts.
- The spec must specify which cloud platform the integration runtime will run on (AWS, Azure, or GCP). If not confirmed in the intent, carry as an open item.
- The spec must include a **monthly infrastructure cost estimate**, even a rough range. Typical ranges:
  - Simple event-driven integration (Lambda + SQS + Secrets Manager + CloudWatch): $20–$60/month
  - Integration with file processing (S3, Step Functions): $40–$100/month
  - High-volume or bidirectional integration: $80–$200/month
- If the cloud platform is unconfirmed, estimate based on AWS as the default.

## Code Warranty

- The implementation vendor covers defects in its own code for **10 business days after go-live**.
- The following are **not covered** by the warranty:
  - Infrastructure failures (cloud provider outages)
  - Third-party API changes (target system changes its API)
  - Data quality issues (bad data in the source system)
  - Configuration changes made by the client after go-live
- The warranty scope must be noted in the **Costs and Ownership** section of every spec.

## Access Model

- The implementation vendor has access to the client's sandbox environment during development.
- Access to the production environment is time-limited (typically 30 days post go-live) and must be logged.
- The implementation vendor must not have standing production access after the warranty period unless explicitly agreed.

## Concern Triggers Summary

| Situation | Concern to flag | Owner |
|-----------|----------------|-------|
| Cloud platform not confirmed | "Cloud platform for integration runtime is not confirmed. This spec assumes AWS — confirm before build to avoid cost estimate revision." | Engineering Lead / Client IT |
| Infrastructure ownership ambiguous | "Ownership of [component] is not assigned. Confirm whether client or vendor provisions this." | Engagement Partner |
| Implementation vendor referenced as hosting client data | "This spec must not propose that the implementation vendor hosts client data. Revise to specify client-owned infrastructure." | Engagement Partner |
| No cost estimate possible (cloud platform unknown) | "Cost estimate cannot be finalized until cloud platform is confirmed. Range provided is for AWS baseline." | Engineering Lead |
