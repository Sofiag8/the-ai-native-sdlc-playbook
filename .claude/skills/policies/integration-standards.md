# Policy: Integration Standards

Apply these constraints when generating any integration spec. Every integration must implement the patterns below. Flag any gap as an Area of Concern with the owner named.

---

## Error Categories

Every failure scenario in the **Error Handling & Exception Playbook** must be assigned one of these categories:

| Category | Definition | Retry? | Notification |
|----------|-----------|--------|-------------|
| **A — Validation failure** | Record is rejected before any write operation. The data is bad (missing required field, unrecognized value, failed mapping). | No | Notify operations team immediately. |
| **B — Downstream rejection** | Payload was valid and sent, but the target system rejected it (e.g., duplicate detected, constraint violation, permission denied). Human review required. | No (requires human resolution first) | Notify operations team immediately. |
| **C — Exhausted retries** | The integration tried and failed repeatedly due to transient errors (target system unavailable, timeout, 5xx). | Yes — see retry policy below | Alert operations team and engineering. Record quarantined in dead-letter queue. |

**Rule:** The Exception Playbook must cover at least these scenarios for every spec:
1. Required field missing or null (Category A)
2. Field value cannot be mapped (e.g., no matching entry in translation table) (Category A)
3. Target system rejects the payload (Category B)
4. Duplicate record detected (Category B)
5. Target system unreachable after retries (Category C)
6. Inbound confirmation not received within expected window (Category C)

## Retry Policy

- Retry strategy: exponential backoff.
- Minimum attempts: 3. Maximum attempts: 5.
- Base interval: 30 seconds. Maximum interval: 10 minutes.
- Category A errors are **not retried**.
- After exhausting retries, the record is moved to a dead-letter queue and a Category C alert is sent.

## Idempotency

- Every write operation must be idempotent: sending the same payload twice must not create duplicate records.
- The spec must document the **idempotency key pattern** used for each entity, e.g.: `sourceRecordId:operationType:version`.
- If the target system does not natively support idempotent operations, the integration must implement a deduplication check before each write.

## Deduplication

- Before creating a new record in a target system, the integration must check whether a matching record already exists.
- The spec must document the **match key** used to identify existing records (e.g., company name + tax ID, email address, external ID field).
- If the match key is not confirmed, carry this forward as an open item and flag as a concern.

**Concern trigger:** If the intent does not specify a deduplication strategy or match key — flag as a concern with owner: Engineering Lead.

## Logging

Every record processed by the integration must produce a log entry containing:
- Record identifier (source system ID)
- Operation type (create / update / skip / reject)
- Result (success / Category A / Category B / Category C)
- Timestamp (ISO 8601, UTC)
- PII fields must not appear in log output (see integration-security policy)

## Event-Driven vs Polling

- Prefer event-driven (webhook) where the source system supports it.
- If webhooks are not supported or confirmed, use scheduled polling as a fallback.
- The polling interval must be documented in the spec. Default fallback: every 15 minutes.
- The spec must note whether webhook support is confirmed or assumed — if unconfirmed, carry as an open item.

## Configuration Management

- Translation tables, field mappings, and enum value mappings must be maintained as external configuration, not hardcoded.
- Every configuration item must have a named owner responsible for keeping it current after go-live.
- If a configuration item has no documented owner, flag as a concern.

## Concern Triggers Summary

| Situation | Concern to flag | Owner |
|-----------|----------------|-------|
| No deduplication strategy defined | "Match key for deduplication in [system] is not specified. Duplicate records may be created." | Engineering Lead |
| Translation table has no maintenance owner | "Translation table for [entity] has no owner. Records with unmapped values will fail silently after go-live." | Operations team |
| Webhook support not confirmed | "Webhook support in [system] is not confirmed. Polling fallback assumed at 15-minute interval." | Client IT / Vendor |
| Idempotency key not defined | "Idempotency key pattern for [entity] is not specified. Duplicate write risk on retry." | Engineering Lead |
